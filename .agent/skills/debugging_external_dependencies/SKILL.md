# 外部依存システムのデバッグプロトコル

本プロジェクトのように `wttr.in` などの外部サービスからデータを取得するシステムにおいて、不具合や挙動の変化が発生した場合は、以下の手順で原因究明を行うこと。

## 1. 現象の切り分け（コード vs 外部サービス）

「以前は正しく動いていたのに、不具合が発生した」場合、まず以下の順序で確認する。

- **コード変更の有無**: `git log` 等を使用し、当該箇所のコードが最近変更されていないかを確認する。
- **外部データの内容確認**: コードに変更がないにも関わらず挙動が変わった場合、外部サービスから取得しているデータ（APIレスポンス等）の内容が変更された可能性をまず疑う。

## 2. 外部データの現物検証

現在の外部サービスからの生のレスポンスを確認する。

```bash
# 例: APIレスポンスをファイルに保存して構造を確認
curl -s "URL" > debug_response.json
jq '.' debug_response.json
```

## 3. 根本原因の特定と対応方針

調査結果に基づき、以下のいずれかのアプローチを取る。

### ケースA：外部サービスの仕様変更（データの粒度・構造の変化）

今回のように、APIが提供するデータの粒度が変わった（例：市町村名が町名になった）場合、単なるコード上のパース調整では解決しないことが多い。

- **対応**: 別の取得方法（別フォーマット、別エンドポイント）の検討や、取得データの加工ロジックの再構築を行う。

### ケースB：コード上の潜在的バグ

特定の条件下でのみ発生するバグや、エッジケースの未考慮が原因の場合。

- **対応**: 既存ロジックの修正。

## 4. 対策案策定時の注意

- 外部サービスを使用している場合、「コードを以前の状態に戻せば直る」のか、「サービス側の変更に合わせて、より上位のレベルでの調整が必要か」をまず俯瞰して判断すること。
- 直接的な解決策（パースの修正等）に飛びつく前に、データの現物確認による裏付けを行うこと。
